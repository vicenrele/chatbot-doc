# Design

## Context

The repository is currently a documentation and standards project rather than an implemented application. Its constraints require Python 3.11+, LangChain for RAG orchestration, Streamlit as the presentation layer, independent pipeline tests, preserved source metadata, idempotent ingestion, and configurable model providers. See proposal.md and the technical-documentation-rag spec for motivation and behavior.

## Goals / Non-Goals

**Goals:**

- Keep the first implementation local-first and operationally small.
- Support a mostly static corpus through explicit full index rebuilds.
- Preserve enough document structure and metadata to produce useful citations.
- Keep ingestion, retrieval, generation, configuration, and Streamlit responsibilities separate.
- Make the vector-store boundary replaceable without changing domain behavior.

**Non-Goals:**

- Remote vector databases or multi-user index synchronization.
- Real-time document watching or complex incremental deletion/update workflows.
- Voice, vision, multi-agent orchestration, or long-term conversation persistence.
- Training or fine-tuning a language or embedding model.

## Decisions

### Pipeline boundaries

Use separate modules for configuration, domain models, ingestion, retrieval, generation, and Streamlit presentation. Streamlit owns session state and rendering; it does not own parsing, chunking, index construction, or prompt policy.

The core flow is:

```text
documents -> validation/loaders -> normalization/chunking -> embeddings
          -> FAISS + chunks metadata + manifest -> retriever
          -> grounded prompt/LLM -> answer and citations -> Streamlit
```

### File loading and chunking

Use LangChain loaders suitable for PDF and Markdown. Preserve PDF page metadata and derive Markdown title/section metadata from headings. Apply structure-aware splitting first where possible, then a recursive splitter for oversized sections. Store deterministic chunk IDs derived from source identity, content hash, and chunk position.

This is preferred over treating every file as plain text because headings, code blocks, and PDF pages materially improve retrieval and citations.

### FAISS persistence

Use FAISS for the local vector index because the corpus is almost static and can be rebuilt as a complete snapshot. Persist three related artifacts in the configured index directory:

- `index.faiss`: vector index.
- `chunks.json`: chunk text, deterministic IDs, and citation metadata in the same order used by the index.
- `index_manifest.json`: corpus hash, embedding provider/model, vector dimensions, distance strategy, ingestion version, and counts.

A build operation computes a corpus hash before indexing. Startup and query paths validate the manifest before opening the index. A mismatch requires an explicit rebuild rather than silently mixing incompatible embeddings or metadata.

FAISS is exposed through a small vector-store adapter. The adapter boundary keeps a future ChromaDB implementation possible, but the initial design does not implement both providers.

### Retrieval and grounding

Use a configurable top-k value and score threshold. Retrieval returns typed evidence objects containing chunk ID, source identity, score, rank, and citation fields. Generation receives only bounded retrieved context and a prompt that treats document text as untrusted evidence, requires citations, and instructs the model to abstain when evidence is insufficient.

Conversation history can help resolve follow-up questions, but it never replaces retrieval from the current index. Provider failures, empty indexes, no-result retrieval, and insufficient context remain distinct application states.

### Streamlit lifecycle

Cache model clients, embedding clients, and a compatible loaded index with `st.cache_resource`. Tie cache invalidation to the manifest or index identity so reruns do not rebuild embeddings. Keep chat messages in `st.session_state` for the active session only. Show index status and source details, while handling detailed exceptions through logging rather than exposing them to users.

### Security and trusted persistence

Treat uploaded or configured source files as untrusted input: enforce file size/count limits, prevent path traversal, and never execute embedded content. Only load persisted FAISS auxiliary files generated by the application in a trusted local directory; do not enable unsafe deserialization for arbitrary user-provided files. Redact credentials, raw embeddings, full document content, and sensitive questions from logs.

### Testing strategy

Use fake embeddings, loaders, vector stores, and chat models for the default test suite. Cover validation, PDF page and Markdown section metadata, deterministic IDs, idempotent rebuilds, manifest incompatibility, relevant and irrelevant retrieval, grounding/refusal behavior, citations, provider errors, and pure Streamlit formatting helpers. Keep provider-backed tests opt-in.

## Risks / Trade-offs

- **[Risk]** Full rebuilds become slow as the corpus grows. -> **Mitigation:** keep the corpus-size limit explicit, report progress, and defer incremental indexing until measurements require it.
- **[Risk]** A changed embedding model can make an old FAISS index unusable. -> **Mitigation:** store and validate model identity and dimensions in the manifest; require an explicit rebuild.
- **[Risk]** FAISS does not own rich metadata or citation presentation. -> **Mitigation:** persist `chunks.json` with a strict positional contract and validate counts/IDs when loading.
- **[Risk]** PDF extraction can lose layout, tables, or scanned text. -> **Mitigation:** report empty/low-content files, preserve page boundaries, and make OCR a future explicit capability rather than silently assuming it.
- **[Risk]** Retrieved documents may contain prompt-injection text. -> **Mitigation:** delimit retrieved evidence, treat it as data, and enforce a grounded generation policy.

## Migration Plan

1. Add the application modules and configuration without requiring an existing index.
2. Run the explicit ingestion/build command against the configured documents directory.
3. Start Streamlit and verify index compatibility before enabling chat queries.
4. To roll back, stop using the generated application/index directory and restore the previous source tree; generated FAISS artifacts are disposable and must not be treated as source of truth.

## Open Questions

- Which embedding provider and model will be selected for the first deployment? This can remain configuration-driven without changing the retrieval contract, provided dimensions and model identity are recorded in the manifest.
- Will PDFs include scanned pages? If so, OCR support should be added as a separate capability after measuring the initial corpus.
